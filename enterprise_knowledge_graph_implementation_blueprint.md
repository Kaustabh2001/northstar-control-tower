# Enterprise Knowledge Graph and Incident Intelligence Platform
## Detailed POC Architecture and Implementation Blueprint

**Document intent:** This is the canonical context document for engineers and coding agents implementing the POC. It describes what is being built, why each data source exists, what is persisted in the knowledge graph, what remains query-only, how historical incidents are converted into useful knowledge, and the high-level coding sequence required to build the system.

---

## 1. Executive Summary

The system is an enterprise knowledge graph centered on a **ServiceNow Business Application**. The graph connects the business/service model, the PROD application instance, its CMDB configuration items (CIs), a runtime application topology derived temporarily from **30 days of AWS X-Ray traces**, Backstage metadata, repository-level code graphs generated by **Graphify**, and historical operational records such as incidents and changes.

The POC deliberately separates **persistent knowledge** from **live evidence**:

- **Persistent knowledge in Neo4j:** business application, PROD instance, CMDB CIs, the temporary X-Ray-derived runtime topology, repository links, Graphify code subgraphs, incidents/changes, historical enrichment results, and embeddings/vector indexes.
- **Authoritative metadata queried from Backstage:** ownership, repository, resource identity and related technical metadata for runtime nodes. A normalized subset may be cached on graph nodes for joins and usability, but Backstage remains authoritative.
- **Live evidence queried only when investigating a new incident:** AWS X-Ray traces/service behavior, CloudWatch logs, Kubernetes pod/deployment/event data, deployment history, and other observability evidence. These are exposed to the agent through bounded MCP tools rather than dumped wholesale into the knowledge graph.

The initial POC is **PROD only**. TST/ACC and other environments are part of the eventual model but are not required to prove the concept.

Historical incidents are not useful enough when represented only as text attached to a CI. Therefore, after the base graph is built, an **historical enrichment agent** must inspect each past incident/change and determine which runtime component(s) in the application graph were actually affected, which component was likely the root cause when supported by evidence, and what resolution pattern or related change was involved. If the evidence is insufficient, the agent must explicitly return `INSUFFICIENT_EVIDENCE` or `AMBIGUOUS` rather than invent a mapping.

For new incidents, the agent first resolves the incident to its CI/application context, performs semantic search over historical incidents, uses matched historical topology as hypotheses, and then validates or rejects those hypotheses with live X-Ray/log/Kubernetes/deployment/code evidence until a hotspot/root cause can be identified.

## 2. POC Scope

### 2.1 In scope

1. One domain or bounded set of applications.
2. PROD application instance only.
3. ServiceNow Business Application and associated PROD instance.
4. CMDB CIs mapped to the PROD instance.
5. Historical ServiceNow incidents attached to CIs.
6. Historical ServiceNow changes/problems where available and useful.
7. Thirty-day X-Ray trace history converted into a **persistent runtime topology snapshot** for the POC.
8. Mapping each X-Ray/runtime node to Backstage information where possible.
9. Repository discovery from Backstage.
10. One Graphify subgraph per discovered repository.
11. Runtime component to repository/code-graph linkage.
12. Embeddings for incident text and other selected unstructured fields.
13. Neo4j vector/full-text/graph retrieval.
14. Historical incident/change enrichment agent.
15. MCP tools for live X-Ray, CloudWatch, and Kubernetes/deployment investigation.
16. New incident investigation agent built on top of graph retrieval plus live tools.

### 2.2 Explicitly out of scope for the first POC

1. Full enterprise-wide onboarding of every application.
2. TST, ACC and other non-PROD environments.
3. Replacing Backstage or ServiceNow as systems of record.
4. Persisting every live trace, every log line, or every Kubernetes event in Neo4j.
5. Perfect historical root-cause labeling for every incident.
6. Automatic remediation or production write actions.
7. Treating an LLM conclusion as ground truth without evidence/provenance.
8. Building a second vector database unless Neo4j proves insufficient during performance testing.

## 3. Core Design Principles

### 3.1 Business Application is the semantic root

Every application-specific knowledge path starts from the ServiceNow Business Application.

```text
BusinessApplication
    -> ApplicationInstance(PROD)
        -> CMDB CI(s)
        -> RuntimeApplicationGraph
```

This prevents the graph from becoming a collection of disconnected technical resources with no business identity.

### 3.2 Application instance is the environment boundary

The graph should remain a single enterprise graph, but `ApplicationInstance` acts as the logical namespace/root for environment-specific topology.

For the POC:

```text
BusinessApplication
    -> PROD Instance
```

Later:

```text
BusinessApplication
    -> PROD Instance
    -> TST Instance
    -> ACC Instance
```

### 3.3 X-Ray has two different roles

**POC graph-construction role:** Because runtime topology is not yet complete in Backstage, aggregate 30 days of X-Ray traces and temporarily materialize an application runtime graph in Neo4j.

**Permanent incident-time role:** X-Ray remains a live query tool that answers what actually happened in a specific time window. This role continues even after Backstage becomes the structural topology authority.

### 3.4 Backstage is authoritative technical context

Backstage is the source to resolve runtime nodes into technical context such as:

- owner/team,
- repository,
- component/resource identity,
- resource ARN or infrastructure identifiers,
- links/metadata,
- eventual structural topology.

The POC uses Backstage as an enrichment/query source around X-Ray-derived nodes.

### 3.5 Code is a separate graph dimension linked through repositories

Each repository is converted into its own Graphify subgraph. Runtime nodes point to repository nodes. Repository nodes anchor Graphify code entities.

The enterprise graph should not require Graphify to understand ServiceNow or Backstage semantics. The connection is made through the canonical `Repository` node.

### 3.6 RAG is a retrieval capability, not a separate mandatory datastore

Neo4j can host:

- graph traversal,
- vector indexes,
- full-text indexes,
- metadata-filtered retrieval.

Therefore the POC should implement semantic retrieval inside the Neo4j-centered retrieval layer unless testing shows a reason to add another vector store.

### 3.7 Historical similarity creates hypotheses, not conclusions

A similar historical incident may indicate a likely affected area. It must never be treated as proof that the current incident has the same root cause.

### 3.8 Evidence insufficiency is a valid output

Historical enrichment and live investigation agents must be allowed to return:

- `ENRICHED`,
- `PARTIAL`,
- `AMBIGUOUS`,
- `INSUFFICIENT_EVIDENCE`.

Forcing a component label when evidence is weak will poison the knowledge graph.

## 6. Source-of-Truth and Persistence Boundaries

| Information | Authoritative Source | Persist in Neo4j? | POC behavior |
|---|---|---:|---|
| Business Application | ServiceNow | Yes | Canonical business root |
| Application Instance | ServiceNow | Yes | PROD only |
| CMDB CI | ServiceNow CMDB | Yes | Connected to PROD instance |
| Incident/change/problem identity and selected fields | ServiceNow | Yes | Historical and current references |
| Runtime topology | Backstage eventually | Yes for POC snapshot | Derived from 30-day X-Ray traces until Backstage has it |
| X-Ray trace details | AWS X-Ray | No, except aggregated topology/provenance | Query live for investigation |
| Owner/team | Backstage | Selected normalized/cached fields optional | Backstage remains authoritative |
| Repository mapping | Backstage | Yes as canonical repository link | Used to attach Graphify graph |
| Code graph | Graphify output | Yes or imported/linked into Neo4j | Separate namespace per repository/version |
| Incident embeddings | Embedding model | Yes | Vector indexed in Neo4j |
| Raw CloudWatch logs | CloudWatch | No | Query live through MCP |
| Raw Kubernetes logs/events | Kubernetes/EKS | No | Query live through MCP |
| Deployment history | deployment/K8s/build source | Usually no raw bulk history; selected refs may be stored | Query live; persist stable references only if useful |
| Historical agent labels | Enrichment agent with evidence | Yes | Confidence + provenance mandatory |

The rule is simple: **store durable relationships and reusable historical knowledge; query high-volume/time-sensitive evidence at investigation time.**

## 7. Canonical Neo4j Ontology for the POC

The exact property names may evolve, but node identities and relationship meanings should remain stable.

### 7.1 `BusinessApplication`

Purpose: business-level semantic root from ServiceNow.

Recommended properties:

```text
id                  canonical immutable ID
snow_sys_id         ServiceNow sys_id
name                application name
description         selected description
source              "servicenow"
source_updated_at   source timestamp
ingested_at         ingestion timestamp
```

### 7.2 `ApplicationInstance`

Purpose: environment-specific application identity.

POC contains only PROD.

```text
id
snow_sys_id
name
environment = "PROD"
source_updated_at
ingested_at
```

Relationship:

```text
(BusinessApplication)-[:HAS_INSTANCE]->(ApplicationInstance)
```

### 7.3 `ConfigurationItem`

Purpose: CMDB CI connected to application instance and historical tickets.

```text
id
snow_sys_id
ci_name
ci_class
serial/resource identifiers when appropriate
source_updated_at
ingested_at
```

Relationships:

```text
(ApplicationInstance)-[:HAS_CI]->(ConfigurationItem)
(Incident)-[:AFFECTS_CI]->(ConfigurationItem)
(Change)-[:AFFECTS_CI]->(ConfigurationItem)
```

### 7.4 `RuntimeComponent`

Purpose: normalized node derived from the X-Ray runtime topology snapshot for the POC.

Examples:

- service,
- remote service,
- AWS service/resource,
- database endpoint,
- Lambda,
- HTTP downstream,
- queue/topic if observable,
- other runtime endpoint.

Recommended properties:

```text
id
runtime_key
name
component_type
aws_account
region
resource_arn              if resolvable
xray_origin_types         list of observed segment/origin types
first_seen
last_seen
window_start
window_end
trace_count
error_trace_count         if computed
source = "xray_30d_aggregate"
backstage_entity_ref      when resolved
backstage_match_confidence
```

Relationships:

```text
(ApplicationInstance)-[:HAS_RUNTIME_COMPONENT]->(RuntimeComponent)
(RuntimeComponent)-[:CALLS]->(RuntimeComponent)
```

The `CALLS` relationship is an **aggregated observation**, not timeless truth. It should contain the aggregation window and counts.

Recommended edge properties:

```text
window_start
window_end
first_seen
last_seen
trace_count
error_count
fault_count
throttle_count
observed = true
source = "xray"
```

Do not present this edge as a permanent architectural dependency without preserving the time window.

### 7.5 `BackstageEntity` - optional canonicalization node

There are two valid POC options:

**Option 1 - minimal persistence:** store selected Backstage identity/metadata directly on `RuntimeComponent` plus repository/team links.

**Option 2 - explicit source model:** create a `BackstageEntity` node and link runtime components to it.

Recommended if Backstage mappings are non-trivial:

```text
(RuntimeComponent)-[:RESOLVES_TO]->(BackstageEntity)
```

Properties:

```text
entity_ref
kind
namespace
name
resource_arn
source_url
```

Then use separate Team/Repository nodes.

### 7.6 `Team`

```text
id
backstage_entity_ref
name
```

Relationship:

```text
(RuntimeComponent)-[:OWNED_BY]->(Team)
```

### 7.7 `Repository`

Purpose: canonical join point between Backstage and Graphify.

```text
id                      normalized repository identity
provider                github/gitlab/bitbucket/etc
host
organization/project
repo_name
clone_url                controlled/private handling
web_url
backstage_source_ref
last_graphified_commit
last_graphified_at
```

Relationships:

```text
(RuntimeComponent)-[:IMPLEMENTED_BY]->(Repository)
(BackstageEntity)-[:IMPLEMENTED_BY]->(Repository)
```

A repository must be deduplicated before Graphify is run. Ten runtime nodes pointing to the same repository should create one repository graph, not ten copies.

### 7.8 `CodeEntity`

Graphify produces the detailed repository graph. The exact labels depend on Graphify output, but normalize enough metadata to support repo scoping.

Examples:

- Module
- Class
- Function
- APIEndpoint
- DBObject/DBCall
- File
- Symbol

Required namespacing properties:

```text
id
repo_id
commit_sha or graph_version
entity_type
qualified_name
file_path
language
```

Core relationship:

```text
(Repository)-[:HAS_CODE_GRAPH]->(CodeEntity)
```

Graphify-native relationships can remain inside each repo namespace, for example:

```text
CALLS
IMPORTS
CONTAINS
DEFINES
READS_FROM
WRITES_TO
IMPLEMENTS
```

Do not accidentally connect same-named functions from different repositories. Every code entity identity must include the repository namespace and preferably the analyzed commit/version.

### 7.9 `Incident`

```text
id
number
short_description
description
priority
state
opened_at
resolved_at
resolution_text
close_notes
source_updated_at
embedding_text
embedding_model
embedding_version
enrichment_status
enrichment_version
```

Relationships:

```text
(Incident)-[:AFFECTS_CI]->(ConfigurationItem)
(Incident)-[:AFFECTED_COMPONENT {confidence,...}]->(RuntimeComponent)
(Incident)-[:ROOT_CAUSE_COMPONENT {confidence,...}]->(RuntimeComponent)
(Incident)-[:RELATED_CHANGE]->(Change)
```

### 7.10 `Change`

```text
id
number
short_description
description
implementation_plan
backout_plan
start/end timestamps
state
embedding fields if selected
```

Relationships may include:

```text
(Change)-[:AFFECTS_CI]->(ConfigurationItem)
(Change)-[:CHANGED_COMPONENT]->(RuntimeComponent)
(Change)-[:CHANGED_REPOSITORY]->(Repository)
```

### 7.11 `Problem`

Optional for POC if data quality supports it.

```text
(Problem)-[:AFFECTS_CI]->(ConfigurationItem)
```

Recommended for auditability.


## 8. Identity and Cross-System Resolution Strategy

Cross-system identity is one of the most important engineering problems in the POC.

### 8.1 Canonical IDs

Never use display names as the only identity.

Examples:

```text
snow:business_application:<sys_id>
snow:application_instance:<sys_id>
snow:ci:<sys_id>
xray:<account>:<region>:<normalized-runtime-key>
backstage:<kind>:<namespace>:<name>
repo:<provider>:<host>:<org-or-project>:<repo>
code:<repo_id>:<graph_version>:<entity-key>
snow:incident:<sys_id>
snow:change:<sys_id>
```

### 8.2 Runtime node to Backstage matching order

Prefer deterministic identity signals before fuzzy matching.

Suggested order:

1. exact ARN/resource ID,
2. Backstage annotation containing AWS resource identity,
3. known Kubernetes namespace/workload/service identity,
4. explicit service/component metadata,
5. repository/source metadata attached to Backstage component,
6. normalized service-name mapping,
7. fuzzy/name similarity only as a last resort.

Persist `backstage_match_method` and `backstage_match_confidence`.

### 8.3 Repository normalization

Normalize all repo references into one canonical form before deduplication.

Examples that may represent the same repository:

```text
git@host:team/orders.git
https://host/team/orders.git
https://host/team/orders
```

Canonicalize host, org/project, repo name and provider.

## 9. Building the POC Runtime Graph from 30 Days of X-Ray Traces

This is a temporary implementation because Backstage does not yet contain the required runtime application graph.

### 9.1 Goal

Produce a stable, queryable topology snapshot that approximates the runtime application graph observed over the previous 30 days.

### 9.2 Required output

```text
ApplicationInstance(PROD)
    -> RuntimeComponent A
    -> RuntimeComponent B
    -> RuntimeComponent C

RuntimeComponent A -CALLS-> RuntimeComponent B
RuntimeComponent B -CALLS-> RuntimeComponent C
```

Each node/edge must carry observation timestamps and provenance.

### 9.3 Extraction sequence

1. Resolve the AWS account(s), region(s) and POC scope for the PROD application.
2. Define the 30-day time window.
3. Split the window into bounded slices suitable for X-Ray API limits and throttling.
4. Retrieve trace summaries/full traces or equivalent X-Ray data required to reconstruct service interactions.
5. Parse segments and subsegments.
6. Extract candidate runtime entities:
   - service names,
   - origins,
   - AWS resource ARNs/IDs,
   - downstream namespaces,
   - HTTP remote hosts/endpoints,
   - database endpoints where exposed,
   - Lambda/service identities,
   - Kubernetes/ECS metadata when present.
7. Extract observed caller -> callee relationships.
8. Normalize identities to canonical `runtime_key` values.
9. Deduplicate nodes across all time slices.
10. Aggregate duplicate caller/callee edges.
11. Compute useful observation metadata such as first seen, last seen, trace count, errors/faults if available.
12. Write nodes/edges idempotently to Neo4j.
13. Attach all in-scope runtime components to the PROD application instance.
14. Persist extraction run metadata and window boundaries.

### 9.4 Important implementation rule

Do **not** generate one graph node per trace segment occurrence. Build one normalized runtime component node and aggregate observations.

Bad:

```text
Trace1-ServiceA
Trace2-ServiceA
Trace3-ServiceA
```

Good:

```text
RuntimeComponent(ServiceA)
    properties: first_seen, last_seen, trace_count...
```

### 9.5 Scope ambiguity that must be resolved during implementation

The coding team must define how X-Ray traces are restricted to the target application. Possible seed signals include:

- known CIs/resource ARNs,
- known Backstage resources,
- X-Ray service names,
- AWS account/region boundaries,
- tags,
- known entry service(s),
- connected component expansion from seed nodes.

This decision is application/domain specific and should be explicit configuration, not hidden heuristics.

### 9.6 Snapshot freshness

Recommended POC behavior:

- bootstrap with 30 days,
- refresh daily,
- retain `window_start` and `window_end`,
- mark nodes/edges not seen for a configured period as stale rather than immediately deleting them,
- later replace the persistent X-Ray topology source with Backstage topology.

## 10. ServiceNow Ingestion

### 10.1 Business model ingest

For each selected POC Business Application:

1. fetch Business Application record,
2. fetch related application instances,
3. retain only PROD for the POC,
4. fetch CMDB CIs associated with PROD,
5. merge them into Neo4j,
6. create `HAS_INSTANCE` and `HAS_CI` relationships.

### 10.2 Historical incident ingest

For each relevant incident:

1. ingest incident identity and selected text/structured fields,
2. resolve its affected CI from ServiceNow,
3. create `Incident -> AFFECTS_CI -> ConfigurationItem`,
4. do not yet guess the runtime component,
5. queue the incident for embedding and historical enrichment.

### 10.3 Historical change/problem ingest

Use the same pattern:

```text
Change -> AFFECTS_CI -> CI
Problem -> AFFECTS_CI -> CI
```

Do not force direct component links until enrichment provides evidence.

### 10.4 Incremental synchronization

Every source record should have:

- source ID,
- source updated timestamp,
- ingestion timestamp,
- content hash where useful.

Only reprocess embeddings/enrichment when relevant source text or graph context changed.

## 11. Connecting ServiceNow PROD Instance to the X-Ray Runtime Graph

The `ApplicationInstance(PROD)` is the structural bridge between ServiceNow business/CMDB knowledge and the temporary X-Ray-derived application topology.

Preferred representation:

```text
(BusinessApplication)-[:HAS_INSTANCE]->(PROD)
(PROD)-[:HAS_CI]->(CI)
(PROD)-[:HAS_RUNTIME_COMPONENT]->(RuntimeComponent)
```

CIs do not necessarily map one-to-one with every X-Ray node. Keep those as separate dimensions unless an explicit mapping exists.

Where evidence exists, add:

```text
(ConfigurationItem)-[:REPRESENTS_RESOURCE]->(RuntimeComponent)
```

with mapping method/confidence.

This avoids pretending that every runtime node is a ServiceNow CI.

## 12. Backstage Enrichment for X-Ray Nodes

### 12.1 Purpose

For every normalized runtime component, Backstage should answer as much as possible about:

- what technical entity/resource it represents,
- owning team,
- repository/repositories,
- resource ARN,
- component/system metadata,
- useful links/documentation.

### 12.2 Resolver workflow

For each `RuntimeComponent`:

1. collect runtime identity evidence: ARN, service name, namespace, workload, host, origin, tags,
2. query Backstage catalog/API using deterministic identifiers first,
3. score candidate matches,
4. if exactly one sufficiently strong match exists, link it,
5. if ambiguous, record candidates and flag unresolved rather than selecting arbitrarily,
6. fetch repository/source location(s), owner/team, resource annotations and metadata,
7. normalize repository references,
8. upsert `Team` and `Repository` nodes,
9. create `OWNED_BY` and `IMPLEMENTED_BY` relationships,
10. store Backstage entity reference and mapping provenance.

### 12.3 Queryable vs persisted

Backstage remains authoritative. Persist only the identity and relationship information needed to construct and efficiently query the graph. Avoid copying every Backstage field into Neo4j.

The agent-facing system may also expose a `get_backstage_context(runtime_component_id)` tool for live authoritative lookup.

## 13. Repository Discovery and Graphify Integration

### 13.1 Repository discovery

After Backstage enrichment:

```text
RuntimeComponent A -> Repo X
RuntimeComponent B -> Repo X
RuntimeComponent C -> Repo Y
```

Deduplicate to:

```text
Repo X
Repo Y
```

Then Graphify each repository once.

### 13.2 Graphify workflow

For each unique repository:

1. resolve authenticated clone/fetch source,
2. determine graph version:
   - for initial POC, configured branch HEAD is acceptable,
   - persist exact analyzed commit SHA,
3. run Graphify,
4. validate Graphify output,
5. import or link Graphify nodes/relationships under the repository namespace,
6. create `(Repository)-[:HAS_CODE_GRAPH]->(CodeEntity)` anchor relationships,
7. store Graphify version, commit SHA and run timestamp,
8. connect every runtime component whose Backstage source points to that repository using `IMPLEMENTED_BY`.

### 13.3 Versioning rule

A code graph without its analyzed commit/version is unsafe. Always store `graph_version` or `commit_sha`.

For future deployment-aware investigation, the system should be able to map:

```text
running image/artifact
    -> build
    -> exact Git SHA
    -> matching Graphify graph version or code diff
```

The POC may start with latest analyzed repo state, but the schema must allow versioned code graphs later.

## 14. Embeddings and Semantic Retrieval

### 14.1 What should be embedded first

POC minimum:

- incident `short_description`,
- incident `description`,
- useful resolution/close notes,
- optionally agent-generated normalized symptom summary.

Recommended `embedding_text` construction:

```text
[short_description]
[description]
[relevant resolution text]
```

Avoid embedding irrelevant identifiers repeatedly if they dominate semantic similarity.

### 14.2 Metadata stored with every embedding

```text
entity_id
entity_type
embedding_model
embedding_version
embedding_created_at
text_hash
```

Re-embed when the text hash changes or the embedding model/version changes.

### 14.3 Neo4j indexes

Create:

1. vector index for Incident embeddings,
2. optional vector index for Change embeddings,
3. full-text index across incident number/title/description where useful,
4. graph-property indexes/constraints on canonical IDs and source IDs.

### 14.4 Retrieval strategy

Do not perform a blind enterprise-wide vector search first.

Preferred widening strategy for a new incident:

**Scope 1 - same CI**

```text
current incident -> affected CI -> historical incidents on same CI
```

Then vector-rank within that set.

**Scope 2 - same PROD application instance**

If too few results, search historical incidents attached to other CIs under the same instance.

**Scope 3 - affected/neighboring runtime components**

Once a candidate hotspot exists, search incidents historically enriched to that component or immediate dependencies.

**Scope 4 - broader domain**

Only widen further when local context is insufficient.

This combines deterministic graph context with semantic similarity and reduces false matches.

## 15. Historical Incident and Change Enrichment Agent

This is the mechanism that converts raw historical tickets into topology-aware operational knowledge.

### 15.1 Objective

Given a historical ServiceNow incident/change and its graph context, determine:

1. which runtime component(s) were affected,
2. which component was the probable root cause if supported,
3. whether a related change/deployment/repository can be established,
4. normalized symptoms,
5. resolution pattern,
6. confidence and evidence,
7. or explicitly that evidence is insufficient.

### 15.2 Inputs

For an incident:

- incident number and timestamps,
- short description,
- description,
- comments/work notes if permitted,
- resolution/close notes,
- related problem/change references,
- affected CI,
- application instance,
- candidate runtime topology around the instance/CI,
- Backstage context for candidate runtime nodes,
- optionally semantic matches to other enriched incidents,
- historical deployment/change evidence if accessible.

### 15.3 Candidate generation before LLM reasoning

Do not give the model the entire enterprise graph.

Candidate scope should be generated deterministically:

1. incident -> CI,
2. CI -> PROD instance,
3. instance -> runtime graph,
4. if CI maps to a runtime component, start there,
5. otherwise use CI/resource metadata and ticket text to rank candidate runtime nodes,
6. expand one or two graph hops as configured,
7. present a bounded candidate list to the agent.

### 15.4 Required structured output

The enrichment agent should return machine-validated JSON similar to:

```json
{
  "status": "ENRICHED",
  "affected_components": [
    {
      "runtime_component_id": "...",
      "confidence": 0.86,
      "evidence": ["incident.description", "work_note:123", "change:CHG001"]
    }
  ],
  "root_cause_component": {
    "runtime_component_id": "...",
    "confidence": 0.74,
    "evidence": ["resolution_notes", "related_change"]
  },
  "symptom_summary": "...",
  "resolution_pattern": "...",
  "related_change_ids": ["..."],
  "related_repository_ids": ["..."],
  "ambiguities": [],
  "evidence_summary": "Concise auditable explanation, not hidden chain-of-thought."
}
```

Valid statuses:

```text
ENRICHED
PARTIAL
AMBIGUOUS
INSUFFICIENT_EVIDENCE
FAILED
```

### 15.5 Evidence threshold policy

The model must not create a `ROOT_CAUSE_COMPONENT` relationship merely because a component name appears in the incident.

Suggested policy:

- `AFFECTED_COMPONENT` may be created at moderate confidence when the ticket clearly describes impact in that component.
- `ROOT_CAUSE_COMPONENT` requires stronger evidence from resolution notes, a related change, deployment evidence, or explicit troubleshooting outcome.
- below threshold, store agent output/audit run but do not create authoritative-looking graph relationships.

Threshold values should be configurable and validated on a human-labeled evaluation set.

### 15.6 Persistence

On successful enrichment:

```text
(Incident)-[:AFFECTED_COMPONENT {confidence, method, run_id}]->(RuntimeComponent)
(Incident)-[:ROOT_CAUSE_COMPONENT {confidence, method, run_id}]->(RuntimeComponent)
(Incident)-[:RELATED_CHANGE]->(Change)
```

Also persist:

- enrichment status,
- agent/prompt/model version,
- evidence references,
- timestamp,
- structured symptom/resolution summary,
- whether a human validated the result.

### 15.7 Human review loop

For POC quality control, sample enrichment results into a review set:

```text
AGREE
PARTIALLY_CORRECT
WRONG_COMPONENT
UNSUPPORTED_ROOT_CAUSE
SHOULD_HAVE_BEEN_INSUFFICIENT
```

Use this evaluation to tune candidate generation, prompt/skill logic and confidence thresholds.

## 18. New Incident Investigation Agent

### 18.1 High-level reasoning loop

```text
New ServiceNow Incident
    -> resolve CI
    -> resolve Business Application + PROD Instance
    -> retrieve local graph context
    -> semantic search similar historical incidents
    -> use historical affected areas as hypotheses
    -> query live X-Ray for incident window
    -> rank current hotspots
    -> investigate hotspots with logs/K8s/deployment evidence
    -> inspect code/repository when needed
    -> validate/eliminate hypotheses
    -> identify root cause or return insufficient evidence
```

### 18.2 Detailed sequence

1. Fetch the new incident.
2. Resolve affected CI.
3. Resolve PROD application instance and Business Application.
4. Retrieve the relevant runtime graph neighborhood.
5. Embed/use current incident text to find similar historical incidents.
6. Extract candidate affected/root-cause components from historical matches.
7. Treat those as hypotheses with scores, not truths.
8. Query X-Ray during the actual incident window.
9. Look for:
   - error/fault spikes,
   - abnormal latency,
   - failed downstream calls,
   - changes in dependency behavior,
   - concentration of failing traces.
10. Rank hotspots.
11. For each hotspot, gather:
   - CloudWatch application logs,
   - Kubernetes/container logs,
   - pod events/restarts,
   - deployment history,
   - exact running image/artifact,
   - recent relevant change records,
   - dependencies,
   - repository and code graph context.
12. Eliminate hypotheses inconsistent with current evidence.
13. Expand to upstream/downstream nodes if evidence points elsewhere.
14. Return:
   - probable hotspot/root cause,
   - confidence,
   - evidence references,
   - competing hypotheses,
   - remediation suggestion only when supported,
   - `INSUFFICIENT_EVIDENCE` if no defensible conclusion exists.

### 18.3 Agent state

The investigation agent should maintain explicit structured state rather than relying only on chat history:

```text
incident_context
candidate_components
hypotheses[]
evidence[]
rejected_hypotheses[]
open_questions[]
current_hotspots[]
conclusion_status
```

This makes multi-step investigation reproducible and debuggable.

## 26. Failure Modes and Required Behavior

### X-Ray API throttling / partial windows

- retry with backoff,
- checkpoint time slices,
- mark extraction run partial,
- never silently publish an incomplete 30-day graph as complete.

### Runtime node cannot be matched to Backstage

- keep X-Ray runtime node,
- mark Backstage status unresolved,
- allow later re-resolution.

### Multiple Backstage candidates

- persist ambiguity/candidates if useful,
- do not choose based only on weak name similarity.

### Repository unavailable or Graphify fails

- keep repository node and runtime linkage,
- mark code graph status failed/pending,
- retry separately.

### Incident has no CI

- mark unresolved input,
- optionally attempt secondary deterministic mapping if approved,
- do not fabricate CI linkage.

### Historical incident has vague text

- `INSUFFICIENT_EVIDENCE`.

### Similar historical incident conflicts with live X-Ray

- live current evidence wins for current-incident reasoning,
- historical match is demoted/rejected.

### No clear root cause in new incident

- return the best-supported hotspots and missing evidence,
- do not force a root-cause conclusion.

## 33. Rules for Any Coding LLM Implementing This System

1. **Do not redesign the ontology casually.** Business Application -> PROD Instance -> CI is the structural spine.
2. **Do not persist raw logs or all traces in Neo4j.** Only aggregate topology/provenance from the 30-day X-Ray bootstrap; live evidence stays query-only.
3. **Do not treat Backstage as a copied database.** Use it as authoritative technical context and persist only required normalized relationships/IDs.
4. **Do not Graphify the same repository repeatedly because multiple runtime nodes point to it.** Deduplicate repository identity first.
5. **Every code graph must have a repository namespace and graph version/commit SHA.**
6. **Do not create historical affected/root-cause links until the base topology exists.**
7. **Historical enrichment must use a strict output schema and evidence references.**
8. **`INSUFFICIENT_EVIDENCE` is preferred over a guessed component.**
9. **Semantic similarity is a retrieval signal, not proof.**
10. **For new incidents, similar incidents produce hypotheses; current X-Ray/log/K8s evidence validates them.**
11. **Never analyze repository HEAD when deployment-specific code evidence is available. Resolve the running artifact to exact Git SHA.**
12. **All high-volume MCP calls must be time-bounded and result-bounded.**
13. **All graph writes must be idempotent.**
14. **All cross-source mappings require provenance/match method and preferably confidence.**
15. **Agent-generated graph facts must be distinguishable from source-of-truth facts.**
16. **Do not give the LLM the entire graph. Generate bounded candidates and context.**
17. **Preserve source timestamps and freshness.**
18. **Implement adapters around ServiceNow, X-Ray, Backstage, Graphify and embedding providers so each can evolve independently.**
19. **Build and evaluate the knowledge foundation before building the final autonomous investigation agent.**
20. **When requirements are ambiguous, expose the ambiguity as configuration or an open decision rather than inventing hidden assumptions.**

## 34. Condensed End-to-End Build Narrative

The POC begins by taking the ServiceNow Business Application and creating its PROD `ApplicationInstance`. The PROD CMDB CIs are attached below it, and historical incidents/changes are attached to the relevant CI records.

Because Backstage does not yet expose the required runtime graph, the system collects 30 days of X-Ray traces, normalizes the service/resource identities observed in those traces and aggregates caller/callee observations into a temporary runtime application graph. That graph is attached to the PROD application instance and carries an explicit 30-day observation window.

Each runtime node is then resolved against Backstage. Backstage provides authoritative technical metadata such as the owning team, resource identifiers and repository source. Repository references are normalized and deduplicated. Each unique repository is analyzed once using Graphify, producing a separate repository-scoped code subgraph, which is connected back to every runtime component implemented by that repository.

The resulting Neo4j graph therefore connects business identity, PROD environment, CMDB, runtime topology, ownership/repository context, code structure and raw historical tickets. Incident text is embedded and stored in Neo4j vector indexes so semantic retrieval can operate together with graph scoping.

Next, an offline historical enrichment agent processes old incidents/changes. For each ticket, deterministic graph traversal first limits the candidate runtime components. The agent then uses the ticket evidence to identify affected components, probable root-cause component where justified, related changes/deployments and normalized symptoms/resolution patterns. Results are persisted with confidence, evidence and provenance. Tickets lacking enough evidence remain explicitly unresolved.

For a new incident, the investigation agent resolves the CI/application context and semantically searches the enriched history. Similar incidents provide starting hypotheses and likely graph regions. The agent then queries live X-Ray for the incident window to identify current runtime hotspots. Each hotspot is investigated using CloudWatch logs, Kubernetes logs/events, deployment history, exact deployed artifact/Git SHA, dependency context and the Graphify code graph. Historical knowledge guides the search, but current live evidence decides whether a hypothesis is accepted or rejected. The process ends with a supported conclusion or an explicit insufficient-evidence result.

The long-term evolution is straightforward: once Backstage contains the authoritative runtime topology, replace the POC X-Ray topology builder with a Backstage topology adapter. X-Ray remains as a live observability tool. The knowledge ontology, semantic history, code graphs, MCP contracts and investigation workflow remain largely unchanged.
