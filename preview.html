Team-lead overview · conceptual architecture

Enterprise Knowledge for Agentic Issue Resolution

How we can give an issue-resolution agent the structured understanding, historical experience and evidence-retrieval ability of a human resolver—while letting it investigate more possibilities, faster.

The idea in one sentence

Build a navigable model of the enterprise, use the graph to decide where to search, use hybrid RAG to decide what evidence is relevant, and expose the whole capability to agents through governed MCP tools.

01 · What we are trying to achieve

Turn scattered enterprise data into usable troubleshooting knowledge

Today, a resolver manually moves across service catalogs, incidents, changes, runbooks, code and runtime systems. The target is not simply a chatbot over documents; it is a knowledge and retrieval layer that supports the same investigation process.

Understand

What the system is

Applications, capabilities, components, APIs, resources, dependencies and owners.

Trace

How it is implemented

Repositories, files, symbols, configuration, builds, deployments and environment snapshots.

Remember

What happened before

Incidents, changes, symptoms, root causes, work notes, timelines and resolutions.

Investigate

What may explain this issue

Form hypotheses, retrieve evidence, eliminate weak paths and deepen promising ones.

Management takeaway

The outcome is an externalized troubleshooting memory and investigation space—not merely a larger RAG index.

04 · Why this scales better than global RAG

Do not ask vector search to find one answer across the whole enterprise

The concern at large scale is not whether a vector database can store millions of vectors. It is retrieval quality: more unrelated but semantically similar content creates more distractors.

Naive approach
100M → top 10

Search everything globally

Incidents, code, documentation, infrastructure and generic text all compete in one similarity search. The top results can look relevant while being operationally wrong.

Our approach
100M → 5K → 100 → 10

Constrain, retrieve, rerank

Use graph relationships and explicit context to produce a candidate universe, run hybrid retrieval inside it, rerank the best evidence, then re-enter the graph.

Core modelling decision: prefer node-based graph scoping over copying the entire parental hierarchy into vector metadata. Hierarchy remains in the graph; search metadata carries only intrinsic properties and the graph node ID.
05 · How the agent behaves

Mimic the human resolver—but explore hypotheses more systematically

A human checks one possibility after another. The agent can keep several plausible branches alive, gather evidence for each and stop expanding branches that become unlikely.

01 · OBSERVE
Characterize the issue

Symptom, service, environment, time and identifiers.

02 · HYPOTHESIZE
Generate possibilities

Deployment, DB, config, dependency, capacity, network or code.

03 · RETRIEVE
Find evidence

Graph paths, similar incidents, recent changes and runtime state.

04 · UPDATE
Score the branches

Record supporting, contradicting and missing evidence.

05 · CONCLUDE
Act or escalate

Return the best-supported cause and the next safe action.

Mental model

The knowledge graph is the navigable model. Search/RAG is the evidence-finding mechanism. The agent is the investigation algorithm. Historical incidents are experience.

07 · One end-to-end investigation

From “login fails after OTP” to evidence-backed cause

The agent alternates between graph traversal and retrieval instead of loading the entire graph or searching every enterprise document.

New incident

Users cannot log in after OTP; requests time out in PROD.

↓
Map the language

Login → authentication capability → authentication-api.

Search similar history

Hybrid retrieval finds a prior incident involving connection-pool exhaustion.

Check recent change

The graph links the service to a deployment and related pool configuration change.

↓
Recover state at incident time

PROD artifact, commit and effective configuration—not only today’s state.

Follow the implementation

Only now inspect the relevant resource, config key, code path and runbook.

↓
Evidence-backed hypothesis

Symptom observed on the login flow; authentication-api affected; identity database pool configuration is the likely root cause. Return evidence, confidence and next validation step.

08 · Practical implementation path

Start with one application and prove the loop

We should validate the model and retrieval behavior against real incidents before scaling across every application, repository and operational source.

Phase 1

Choose the pilot

One representative application, its Backstage entities and a useful sample of ServiceNow incidents and changes.

Phase 2

Build usable knowledge

Validate node types, relationship grammar, semantic capability profiles and evidence provenance.

Phase 3

Prove retrieval

Graph scoping, exact search, BM25, embeddings, reranking and a small Knowledge MCP.

Phase 4

Measure the agent

Replay historical incidents; measure evidence recall, cause accuracy, investigation cost and human acceptance.

Known

Backstage is maintained for ownership and broad application/repository structure. ServiceNow incidents and changes are maintained.

Must construct

Capability semantics, exact component-to-code mappings, incident-to-application mapping, search representations and cross-layer relationships.

Unknown / low trust

CMDB topology is not maintained. Access and quality for environment configuration, deployment state, logs, metrics and enterprise ACL normalization must be discovered.

Pilot success

One real incident can be traced from symptom → application → candidate evidence → recent change → deployed state → likely cause, with every conclusion linked to evidence.
