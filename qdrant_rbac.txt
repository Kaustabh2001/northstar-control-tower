Your design fits this pattern well. The only change is **which token the ingress check validates**: your auth server's own token, not Keycloak's. Keycloak drops out of the Qdrant request path entirely; it's only involved when a token is first issued.

## Adapted flow

```text
Login time (already exists):
  user/service → Keycloak (authenticate) → auth server
  auth server: validate KC token → read group → resolve role → issue AUTH-SERVER token

Every Qdrant request (new):
  service ──(auth-server token)──► qdrant.example.com (ingress)
                                        │ subrequest
                                        ▼
                               auth server /qdrant/authz
                               verify OWN token → role → Qdrant permission
                                        │ 200 + api-key header
                                        ▼
                                     Qdrant
```

## What changes vs. what I described earlier

**Keycloak:** you don't need the `qdrant` client, client roles, or audience mapper. Keep your groups and the client your auth server already uses. The group → role mapping stays in your auth server config.

**Ingress:** no change. It's the same `auth-url` and `auth-response-headers: api-key` annotations. Ingress-nginx doesn't care what kind of token it is.

**Auth server config:** add Qdrant permissions to your existing roles/profiles, for example:

```yaml
roles:
  ml-engineer:
    services:
      qdrant:
        access: rw                 # Option A: picks read-write key
  analyst:
    services:
      qdrant:
        access: r
  rag-service:
    services:
      qdrant:
        collections:               # Option B: minted Qdrant JWT
          - { name: docs,    access: r }
          - { name: support, access: rw }
```

**`/qdrant/authz` endpoint:** verify your own token instead of Keycloak's:

```python
@app.get("/qdrant/authz")
def authz(request: Request):
    token = extract_token(request)              # Bearer / api-key header / cookie
    if not token:
        return Response(status_code=401)
    try:
        claims = verify_own_token(token)        # your signing key, iss, exp, aud
    except InvalidToken:
        return Response(status_code=401)

    if is_revoked(claims["jti"]):               # optional, you control this now
        return Response(status_code=401)

    perm = config.roles.get(claims["role"], {}).get("services", {}).get("qdrant")
    if not perm:
        return Response(status_code=403)

    if "collections" in perm:                   # Option B
        key = mint_qdrant_jwt(perm["collections"], ttl=300)
    else:                                       # Option A
        key = QDRANT_RW_KEY if perm["access"] == "rw" else QDRANT_RO_KEY

    return Response(status_code=200, headers={"api-key": key})
```

This is actually simpler than the Keycloak version: validating your own token is a local signature check with no JWKS fetching, and the role is already in the token, so no extra lookup is needed.

## Things to watch in this design

- **Audience:** if your auth-server tokens are accepted by many services, add an `aud` or `services` claim and have `/qdrant/authz` require `qdrant` in it. Otherwise any valid token from your system reaches Qdrant (and then only the role decides).
- **Group changes lag:** if someone is removed from a Keycloak group, their auth-server token keeps its role until it expires. Keep the TTL short or use the `jti` denylist shown above. Since `/qdrant/authz` runs on every request, a denylist check there takes effect immediately.
- **Re-read the role config per request, not from the token alone,** if you want config changes (such as downgrading `rw` to `r`) to apply without reissuing tokens. The code above already does this: the token carries the role name, and the permission is looked up from current config.
- **Dashboard login:** the `/login` redirect goes to *your* auth server's login (which bounces to Keycloak as it does today). After the callback, set the auth-server token in a cookie on `.example.com` so the ingress forwards it to `/qdrant/authz`.
- **SDKs:** services pass the auth-server token as the Qdrant client's `api_key`, or send it as `Authorization: Bearer`. The ingress then swaps it for the real key.

## Alternative: skip the ingress hop entirely

Since your auth server already issues tokens, it could issue a **Qdrant JWT directly**, with `jwt_rbac: true` in Qdrant, signed HS256 with the Qdrant API key and carrying collection grants. Services would call something like `POST /token/qdrant` with their auth-server token, get back a Qdrant JWT, and use it as the `api_key`. Qdrant validates it itself, so no `auth-url` annotation is needed.

| | Forward-auth at ingress | Auth server mints Qdrant JWT |
|---|---|---|
| Per-request latency | Extra hop (cacheable) | None |
| Revocation | Immediate (denylist) | Only at JWT expiry |
| Central audit log | Every request | Only token issuance |
| Client changes | None; send existing token | Fetch and refresh a second token |
| Auth server down | Qdrant unreachable | Existing JWTs keep working |

For high-QPS search traffic, the JWT-minting route with a 5–15 minute TTL is attractive. If you want immediate revocation and a full audit log, keep forward-auth. You can also combine them: mint JWTs for trusted internal services, and use forward-auth on the public ingress.
